# 技術選定理由書（ADR）

## 概要

このドキュメントでは、本プロジェクトで採用した技術とその選定理由を記録する。

ADR（Architecture Decision Records）は、アーキテクチャに関する重要な決定を文書化し、将来の開発者や自分自身が「なぜこの技術を選んだのか」を理解できるようにするためのものである。

**ADR-000** は他のすべての ADR が参照する「想定規模」の共通前提である。ADR-001 以降の「この規模には過剰」という判断の妥当性は、ここに定義した数値に対して検証する。

各 ADR（001 以降）は次の構成を基本とする。

| 節 | 書くこと |
|---|---|
| 前提 | ADR-000 のどの数値に依存するか |
| 理由 | 採用理由に加え、却下した選択肢を公平に評価し、何を優先したかを明示する |
| Consequences | 得たもの（+）と失ったもの・将来の制約（-） |
| 再検討トリガー | 判断が無効になりうる条件 |

---

## ADR-000: 想定規模の前提

### ステータス

暫定（推定値・**リリース後の実測による更新必須**）

### コンテキスト

ADR-001 以降の技術選定では「この規模には過剰」という判断を複数回行っている。しかしその「規模」が定義されていなければ、判断の妥当性を後から検証できず、いつ判断が無効になるのかも分からない。

本 ADR は、他のすべての ADR が参照する共通の前提数値を定義する。
リリース前のため実測値は存在せず、以下はすべて店舗の営業条件から導出した推定値である。

事業上の物理制約（営業日・提供数など）の確定値は [`domain_knowledge.md`](./domain_knowledge.md) を正とする。本 ADR はそれらから導出した負荷・集客の推定と、技術選定への影響範囲を扱う。

---

### 1. 事業上の物理制約（確定値）

店舗営業条件の正は [`domain_knowledge.md`](./domain_knowledge.md) である。本節はその要約と、規模推定用の計算である。

| 項目 | 値 | 出典・注記 |
|---|---|---|
| 定例の営業曜日 | 月・火・水・土・日（木・金は定休日） | `domain_knowledge` |
| 祝日 | 通常営業（11:30–15:00）。祝が日曜に重なる場合も朝営業なし | 同上。定例合成は同梱の内閣府「国民の祝日」CSV で祝日を判定し、曜日より優先して `normal` にする（年 1 回 `make update-holidays` で更新。`docs/holidays.md`）。`daily_schedules` 行があればそちらが正 |
| 営業時間 | 月火水土祝: 11:30–15:00（ランチ）。**日曜は 8:30–15:00（朝営業あり）** | 同上。日曜の朝帯は予約不可・来店順 |
| 提供数（定例デフォルト） | **1日最大10食**（オーナーが日ごとに変更可能） | 同上。システム上の絶対上限ではない |
| 月間営業日数（定例ベース） | 約21.5日（週5日 × 4.3週） | 計算。祝が木・金に重なると営業日が増えうる |
| **月間提供数の定例理論上限** | **約215食** | 10食 × 21.5日。下記の「天井」の意味を参照 |

**「約215食」の位置づけ**

- 定例デフォルト（週5・1日10食）から導く**規模感の目安**であり、ハードキャップではない。
- 日別の提供数変更、店内イベント、祝日による営業日増、臨時休業・外部イベントによる減により、実月の提供数はこの前後に振れる（イベント等で月+20〜40食程度を見込みうる）。
- 以下の負荷推定は、この定例目安の内側〜その近傍に収まる想定である。

### 3. 導出した前提値

| 項目 | 推定値 | 導出過程 | 確度 |
|---|---|---|---|
| 月間セッション | 300〜800（中央値500） | 上記チャネル別推定の合計 | 低 |
| 月間予約件数 | 60〜120 | 定例上限215食 ÷ 平均1.8名/組 ≒ 119組。稼働率50〜100%を想定（Web・Instagram・電話等の経路合算） | 中 |
| 月間メール送信数 | 120〜300通 | Web予約は顧客向け最大2通（受付確認＋承認。拒否時は受付＋拒否で同様に2通）。オーナー手動登録はメールなし。システム上のキャンセル・変更メールは無し（連絡は Instagram DM） | 中 |
| バックエンドリクエスト | 月1,000〜3,000 | 静的アセットはCloudflareのエッジで完結するため、オリジンに到達するのは空き枠取得APIと予約POST、および管理画面操作のみ | 中 |
| ピーク同時アクセス | 10未満 | Instagram投稿直後・イベント告知直後の1〜2時間に50〜100セッションが集中しても、秒間1リクエストに満たない | 中 |
| DBレコード増加量 | 予約 年間1,000〜1,400件 | 月60〜120件 × 12ヶ月。数年運用してもデータ量は数MB規模 | 中 |

**確度の定義**

- 高: 業務フローから直接算出でき、集客状況に依存しない
- 中: 定例の物理上限が効くため、外しても桁は変わりにくい（または経路・承認結果で通数が振れる）
- 低: 外部要因に依存し、実測との乖離が大きくなりうる

**メール通数の補足**

- 現行の送信種別は顧客向けの受付・承認・拒否のみ（オーナー宛の予約ごと通知は未実装。UC-S04 リマインドは別途）。
- 月間予約の一部は Instagram / 電話等の手動登録のため、メール対象は Web 経路に偏る。上記 120〜300 はその前提の概算である。

### 4. この前提に依存している決定

数値が変わった場合に再検討が必要になる ADR を明示する。

| 前提 | 依存するADR | 前提が崩れた場合の影響 |
|---|---|---|
| 月間メール 120〜300通 | ADR-004（Resend） | 無料枠3,000通/月を超えるとコストが発生。AWS SESへの移行検討が必要 |
| ピーク同時 10未満 | ADR-002（Cloudflare Pages）<br>ADR-008（Cloud Run） | 大幅に超える場合、キャッシュ戦略とスケーリングの検討が必要 |
| 月間セッション 300〜800 | ADR-001（Astro）<br>ADR-002（Cloudflare Pages） | 帯域・ビルド回数ともに無料枠内。桁が変わらない限り再検討不要 |
| 予約 年間1,000件強 | ADR-009（DB・整合性） | データ量・インデックス設計に影響。桁が2つ変わるまで現行構成で十分 |

### 設計上の主リスク

想定トラフィックでは、スケーラビリティ起因の障害は起きにくい。
一方、1日あたりの提供数が小さいため、残り枠が少ないタイミングでの同時予約申込による不整合（オーバーブッキング）が主リスクとなる。
同時予約の整合性は ADR-009 で扱う。

| タイミング | 対応 |

## ADR-001: フロントエンドフレームワーク

### ステータス

採用

### コンテキスト

予約システムのフロントエンドを構築するにあたり、フレームワークを選定する必要があった。静的な店舗紹介と、予約フォーム・管理画面のインタラクションが混在する。

### 前提

- 月間セッション 300〜800（中央値 500）（ADR-000）
- ピーク同時アクセス 10 未満（ADR-000）
- ホスティングは Cloudflare Pages を想定（ADR-002）

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| Next.js | 情報量多い、フルスタック | この規模には過剰。Cloudflare Pages では Node 固有 API・一部 Middleware / SSR パターンが制限され、回避策の調査コストが乗る |
| Astro + React | 静的は JS 0KB、必要な部分だけ React | Island 間で React Context が共有できない。学習コストあり |
| React + Vite (SPA) | シンプル | SEO・初期表示で静的配信の利点を捨てる |
| Nuxt 3 | Vue 向けに最適 | React 経験を活かせない |

### 決定

**Astro + React（Islands Architecture）** を採用

### 理由

- トップ・取引先は静的、予約・管理はインタラクティブ、というページ構成に Islands が直接対応する
- Cloudflare Pages の静的出力と相性が良く、Next.js を Cloudflare 向けにねじ込む調査コストを避けられる
- React の知識を Island 内でそのまま使える

却下の要点: Next.js は情報量で勝るが、想定セッション数百ではフルスタックの恩恵が薄く、Cloudflare 上の制限回避が初期工数になる。情報量より、静的配信形態との一致を優先した。

### Consequences

- (+) 静的ページを JS 0KB で配信できる
- (+) 予約フォーム等は React で実装できる
- (-) Island をまたぐ状態共有に React Context が使えない。共有が必要になった時点で nanostores 等の追加判断が発生する
- (-) Astro 固有の慣習・ビルド設定の学習コストがある
- (-) 管理画面を大きく SPA 化すると Islands の利点が薄れ、構成を見直す圧力がかかる

### 再検討トリガー

- Island 間の共有状態が複数機能にまたがり、アドホックな受け渡しが保守不能になった場合
- 月間セッションが 2,000 を超え、SSR / エッジ動的レンダリングが必要になった場合（ADR-000）

## ADR-002: ホスティング（フロントエンド）

### ステータス

採用

### コンテキスト

フロントエンドのホスティング先を選定する必要があった。ドメインは Cloudflare Registrar を利用する想定。

### 前提

- 月間セッション 300〜800（ADR-000）
- フロントは Astro 静的出力（ADR-001）

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| Vercel | Next.js 最適化、情報多い | 帯域課金。この規模では機能過多になりやすい |
| Cloudflare Pages | 帯域無制限（無料枠）、CDN、DNS と一元管理 | Next.js 向け情報が Vercel より少ない（本プロジェクトは Astro 静的のため影響小） |
| Netlify | 使いやすい | 帯域に制限あり |

### 決定

**Cloudflare Pages** を採用

### 理由

- 帯域無制限の無料枠で、想定セッションでは料金が発生しにくい
- ドメイン（Cloudflare）と DNS・Pages を一元管理できる
- Astro の静的出力と一致する

却下の要点: Vercel は DX で勝るが、帯域課金と Next 最適化の恩恵が現状の構成では薄い。Cloudflare への一本化による運用の単純さと、コスト上限の予測可能性を優先した。

### Consequences

- (+) 静的配信・CDN・DNS が同一ベンダーで完結する
- (+) 想定規模では無料枠内に収まりやすい
- (-) Node.js 固有 API に依存するライブラリやビルド手順は使えない／使いにくい場面が出る
- (-) 高度なエッジ SSR や Next 専用機能を後から足すと、プラットフォーム制約に当たりやすい

### 再検討トリガー

- 月間セッションが 2,000 を超えた場合（ADR-000）
- Node 依存のビルドやランタイムが必須になり、Pages の制約回避コストが継続的に発生した場合

## ADR-003: スタイリング

### ステータス

採用

### コンテキスト

UI のスタイリング手法を選定する必要があった。

### 前提

- フロントは Astro + React Islands（ADR-001）
- 1 人開発で速度を優先する

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| Tailwind CSS | 開発速度、一貫性 | クラス名が長くなる |
| CSS Modules | スコープ明確 | ユーティリティより手が遅い |
| 素の CSS | 学習コスト 0 | 規模が増えると管理が難しくなる |
| CSS-in-JS | コンポーネント完結 | Astro との相性が弱い |

### 決定

**Tailwind CSS v4 + 必要箇所のカスタム CSS** を採用

### 理由

- ユーティリティで画面を素早く組み立てられる
- Astro 公式系の統合があり、未使用クラス除去と相性が良い
- 複雑なアニメーションのみ `<style>` で補う

却下の要点: CSS Modules はスコープは明確だが、この規模・人数では速度差が効く。見た目の一貫性を短時間で出すことを優先した。

### Consequences

- (+) 画面実装の速度とデザインの一貫性を取りやすい
- (-) マークアップのクラスが長く読みにくくなる
- (-) デザインシステムを厳密に育てる場合、トークン設計を別途整える必要がある

### 再検討トリガー

- コンポーネント数が増え、ユーティリティの重複・ばらつきがレビューコストを支配し始めた場合

## ADR-004: メール送信サービス

### ステータス

採用

### コンテキスト

予約の受付確認・承認・拒否など、顧客向け通知メールの送信サービスを選定する必要があった。

### 前提

- 月間メール送信数 120〜300 通（ADR-000）
- ピークでも 1,000 通/月を超えない見込み（ADR-000）
- バックエンドは Go（ADR-007）

### 検討した選択肢

| 選択肢 | 無料枠 | メリット | デメリット |
| --- | --- | --- | --- |
| SendGrid | 100 通/日 程度の枠（プラン依存） | 実績豊富 | API・ダッシュボードが重く、この規模では過剰 |
| Resend | 3,000 通/月 | API がシンプル、Go SDK あり | 比較的新しい。到達率チューニング手段は SES より限られる |
| AWS SES | 62,000 通/月 | 無料枠が桁違いに大きい、最安水準 | SPF/DKIM/サンドボックス解除などに初期数時間を要する |

### 決定

**Resend** を採用

### 理由

- Go SDK があり、実装工数を最小化できる
- SES は無料枠が圧倒的だが、ドメイン認証・サンドボックス解除に初期数時間を要する。現状の想定通数では **Resend / SES とも料金差は実質 $0**
- コスト差ではなく、初期導入工数の小ささを優先した

却下の要点: SES を「設定が複雑」だけで落としたのではなく、無料枠の優位を認識したうえで、月数百通では料金差が出ないため初期導入工数を優先した。

### Consequences

- (+) メール送信の初期実装が最短で済む
- (-) ベンダーが比較的新しく、長期の可用性実績は SES より少ない
- (-) 到達率の細かいチューニング手段は SES より限られる

### 再検討トリガー

- 月間送信が 2,000 通を超えた場合（ADR-000 と同閾値）
- 到達率・バウンスの問題が継続して観測された場合
- → AWS SES への移行を評価する

## ADR-005: バックエンドアーキテクチャ

### ステータス

採用

### コンテキスト

バックエンドのアーキテクチャパターンを選定する必要があった。言語・ホスティング・DB は ADR-007〜009。

### 前提

- ドメイン複雑さは低〜中（予約・スケジュール・取引先）
- チームは 1 人開発
- 月間バックエンドリクエスト 1,000〜3,000（ADR-000）

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| レイヤード + Repository + DI | バランス良い、テスト容易 | 多少のボイラープレート |
| クリーンアーキテクチャ | 疎結合 | この規模・人数には過剰 |
| フル DDD | ドメイン表現力 | 明らかに過剰 |
| シンプル MVC | 学習コスト低 | テスト困難、ハンドラ肥大化 |

### 決定

**レイヤードアーキテクチャ + Repository + DI** を採用

### 理由

- UseCase をモック注入で単体テストできる
- Web フレームワークに依存せず `net/http` で足りる規模
- 必要になった Domains Service（空き枠等）を足せる余白がある

却下の要点: クリーン／フル DDD は将来の差し替え容易性と引き換えにファイル数と間接層が増える。過剰な層を増やさず、テスト容易性を確保する構成を選んだ。

### Consequences

- (+) Handler / UseCase / Repository の境界が明確
- (+) DB 実装を差し替えても UseCase を保てる
- (-) 小さな CRUD でもファイルと型が増える
- (-) 「どこに書くか」の判断を誤ると層をまたいだ依存が生まれる（規約・レビューで防ぐ）

### 再検討トリガー

- 複数人開発になり、層の規約コストが速度を大きく下げた場合
- ドメインが大幅に増え、境界づけられたコンテキスト分割が必要になった場合

## ADR-006: ランタイム・パッケージマネージャ

### ステータス

採用

### コンテキスト

フロントエンドの JavaScript ランタイムとパッケージマネージャを選定する必要があった。

### 前提

- フロントは Astro（ADR-001）
- 本番配信は Cloudflare Pages（ADR-002）。ローカル開発に bun を使う

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| bun | 高速、ランタイム + パッケージマネージャが一体 | Node との一部互換性問題がありうる |
| Node.js + pnpm | 安定、互換性高い | bun より遅い |
| Node.js + npm | 最も安定 | 遅い |

### 決定

**bun** を採用

### 理由

- インストール・スクリプト実行が速く、開発体験が良い
- Astro が公式に bun をサポート
- 本番は Cloudflare 上のビルド成果物を配信するため、ローカルランタイム差の影響は限定的

却下の要点: Node + pnpm は互換性で勝る。互換問題を認識したうえで速度とツールチェーンの単純さを優先し、問題が出たら Node に戻せる前提とした。現状、互換問題は未観測。

### Consequences

- (+) 依存インストールとローカル実行が速い
- (-) bun 固有の不具合やロックファイル差が出た場合、CI / メンバー環境で調査コストがかかる
- (-) 「本番は Cloudflare」でも、ローカルと CI のランタイム差は残る

### 再検討トリガー

- bun 起因のビルド／テスト失敗が繰り返し発生した場合
- CI を Node に揃えた方が総コストが下がると判断した場合

## ADR-007: バックエンド言語

### ステータス

採用

### コンテキスト

API サーバの実装言語を選定する必要があった。

### 前提

- 月間バックエンドリクエスト 1,000〜3,000、ピーク同時 10 未満（ADR-000）
- メール送信など I/O 待ちを非同期にしたい（ADR-004）
- ホスティングはコンテナ想定（ADR-008）

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| TypeScript (Node 等) | 型が書きやすい、フロントと言語統一 | 学習目的の Go 経験が積めない。単一バイナリ配布の単純さは劣る |
| Go | 単一バイナリ、goroutine が簡単、Cloud Run 向き | 型・ジェネリクスの書き味は TS より冗長になりやすい。エコシステムは Web 系で TS に劣る面あり |
| その他（Python 等） | 学習コストが低い場合あり | このプロジェクトの制約・好みと合わない |

### 決定

**Go（標準ライブラリ `net/http`）** を採用

### 理由

- TypeScript も検討し、型の書きやすさでは TS が有利と認識した
- それでも **Go を学習したかった**ことが主因。並列処理（goroutine）を素直に書ける点も評価した（メール送信のインプロセスキュー等）
- 単一バイナリは Cloud Run への載せ方が単純

却下の要点: TS の型 DX より、学習価値と goroutine / デプロイの単純さを優先した。規模が小さいため言語差によるスループット差は判断軸にならない。

### Consequences

- (+) メール等の非同期処理を goroutine ベースで実装しやすい
- (+) コンテナ成果物が単一バイナリで扱いやすい
- (-) フロントとバックで言語が分かれ、型の共有は OpenAPI / 手書き型に依存する
- (-) Go のボイラープレート・エラーハンドリング量が増える

### 再検討トリガー

- バックエンドの機能追加が言語の学習コストを理由に停滞し続けた場合
- フロントとの型共有コストが、API 契約管理の限界を超えた場合

## ADR-009: データベース選定と予約整合性

### ステータス

採用

### コンテキスト

永続化先の選定と、予約システム固有の同時申込（オーバーブッキング）への対応方針を決める必要があった。負荷より整合性が本プロダクトの主リスクである（ADR-000）。

### 前提

- 予約 年間 1,000〜1,400 件程度、数年でもデータ量は数 MB 規模（ADR-000）
- ピーク同時アクセス 10 未満だが、残り僅少枠への同時申込は起きうる（ADR-000）

### 検討した選択肢（ホスト）

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| Supabase（PostgreSQL） | Postgres に慣れている。無料枠で足りそう。ダッシュボードあり | 無料枠の pause（停止）がありうる |
| Neon（PostgreSQL） | Postgres。コールドスタートはあるが pause 感がマシに感じられる場合あり | 慣性が Supabase より薄い（当時） |
| その他マネージド Postgres | 同様 | 学習・移行コスト |

**RLS**: Supabase Auth / RLS は使わず **DB 接続のみ**で利用する想定のため、RLS 設計の複雑さは当面の判断軸から外す。

### 決定

- **データベース**: PostgreSQL on **Supabase**（接続のみ）
- **予約整合性**:
  - 同一 `visit_date` への作成はトランザクション内で **`pg_advisory_xact_lock`**（VisitDateLocker）→ 残数再計算 → INSERT
  - 同一来店日時・電話番号のアクティブ重複は **部分ユニーク制約**（`pending` / `approved`）
  - 定員超過はアプリケーションの残数チェック（`CAPACITY_EXCEEDED`）

### 理由

- Postgres が最も慣れている
- 無料枠で足りそうで、Neon と迷ったが当面は慣れている Supabase を選んだ（pause は認識済み）
- 同時申込はトラフィック規模が小さくても起きうるため、楽観的な「チェックしてから INSERT」だけにしない

### Consequences

- (+) 慣れた SQL / Postgres でスキーマと制約を明示できる
- (+) 来店日単位の直列化で、残数をまたぐレースを抑えられる
- (-) Supabase 無料枠の pause により、開発・稀なアクセスで初回レイテンシが出うる
- (-) advisory lock は「来店日」粒度。別日は並列。ロック待ちの監視は別途必要になりうる
- (-) 部分ユニークは電話番号×日時の重複のみ。定員はアプリ側ロジックに依存する

### 再検討トリガー

- pause / 接続制限が運用上の支障になった場合 → Neon 等への移行を評価
- ロック待ち・タイムアウトが観測された場合 → ロック粒度や待ち時間の設計を見直す
- 予約データ量が桁で増え、インデックス・保管方針（ADR-013）と合わせて見直しが必要な場合

---

## ADR-010: 認証・認可（管理者）

### ステータス

採用

### コンテキスト

管理画面（予約承認、スケジュール、取引先）向けの認証方式を選定する必要があった。顧客向けログインは持たない。

### 前提

- 管理者は少人数（実質オーナー）
- 学習目的を優先してよい規模（ADR-000）

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| Auth0 / Clerk 等の IdP | 実装が速い、セキュリティ機能が揃いやすい | この規模・人数には過剰。コストとベンダーロック |
| Supabase Auth | 同一ベンダーで完結 | DB のみ利用方針と混ざる。学習目的に合わない |
| 自前 JWT（AT + RT Cookie） | 学習になる。挙動を自分で制御できる | 実装・脅威対策を自前で持つ |

### 決定

**自前 JWT**（アクセストークン JSON + リフレッシュトークン Cookie、ローテーション、ログイン失敗レートリミット）を採用

### 理由

- **学習目的が最も大きい**
- 管理者少数のため、IdP の恩恵（ソーシャルログイン、大規模ユーザ管理）が薄い

却下の要点: IdP の安全性・速さは認識したうえで、学習と制御の可視性を優先した。その代わりブルートフォース対策等は自前で入れる。

### Consequences

- (+) トークン寿命・Cookie 属性・失敗上限をプロダクト要件に合わせて変えられる
- (-) 認証実装の不備は直接インシデントになる。レビューとテストを厚くする必要がある
- (-) パスワードリセット・招待フロー等を後から足すと、IdP より工数が大きい

### 再検討トリガー

- 管理者が増え、招待・権限ロール・監査が必要になった場合
- 認証まわりのインシデントまたは繰り返しの脆弱性指摘があった場合 → IdP 移行を評価

## ADR-014: メール送信の Outbox パターン

### ステータス

採用

### コンテキスト

予約受付・承認・拒否の顧客向けメールを、予約成立と分離して確実に再送できるようにする必要があった。インプロセスの揮発キューではプロセス終了や満杯時ドロップで送信意図が失われる。

### 前提

- メール送信サービスは Resend（ADR-004）
- 予約整合性は PostgreSQL トランザクション（ADR-009）
- ステータス遷移は `pending → approved | rejected` のみ（逆向き・相互遷移不可）

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| インプロセス channel キュー | 実装が単純 | プロセス終了で消失、再送なし |
| `reservations.email_sent_at` | カラム 1 本で済む | 論理メール種別ごとの状態を表現しにくい |
| `email_outbox` + ワーカー | 送信意図が永続化され再送可能 | テーブル・flush 運用が増える |

### 決定

- 予約は DB コミット時点で成立とする。メール送信は予約成立の必須条件としない
- 予約 INSERT / ステータス更新と同一トランザクションで `email_outbox` に送信意図（本文レンダリング済み）を記録する。**送信意図の記録は予約操作の必須条件**とし、Tx 外には出さない（enqueue の DB エラーは予約操作ごとロールバック。通知されない予約を作らないため）
- Cloud Scheduler（1 分ごと）が private Cloud Run の `POST /internal/outbox/flush` を叩き、Dispatcher が指数バックオフで送信する
- Dispatcher は **lease 方式**（claim → 送信 → mark をそれぞれ独立してコミット）:
  - claim は単一 UPDATE（`FOR UPDATE SKIP LOCKED` サブクエリ）で `attempt_count + 1` と `next_attempt_at = 今 + lease（5 分）` を確定させる
  - 送信は DB トランザクションの外で行い、1 通ごとに送信タイムアウト（30 秒）を掛ける
  - 送信結果の記録（`MarkSent` / `MarkRetry` / `MarkFailed`）は呼び出し元の cancel から切り離した独立コンテキストで行う
  - 送信中にクラッシュ・cancel されても試行は消費済みなので、ポイズンメッセージは lease 切れごとに 1 回ずつ試行され最大 6 回で `failed` になる
  - 行ごとの mark 失敗はレスポンスの `errors` に数えて次の行へ進む。claim 自体の失敗（DB 断）だけ 500 を返す
- 1 回の flush は `OUTBOX_BATCH_SIZE`（既定 20）件かつ `OUTBOX_FLUSH_TIME_BUDGET_SECONDS`（既定 120 秒）以内。残り予算が送信タイムアウト未満なら次の claim をしない。時間予算は Cloud Scheduler の attempt-deadline（180 秒）より短く保つ
- Resend の 401 / 403（認証・認可）はメッセージ起因ではないので、行の試行を消費させず（`ReleaseClaim`）に **バッチを中断**し、ERROR ログを残す。設定修正後は次の flush で自動再開する
- `ENVIRONMENT=production` かつ flush 有効のサービスでは `RESEND_API_KEY` を必須にし、未設定なら起動失敗させる（NoOp Sender が未送信のまま `sent` を記録することを防ぐ）
- 二重送信対策は二段構え:
  - DB: `UNIQUE (reservation_id, mail_type)`（防御的不変条件。通常フローでは衝突しない）
  - Resend: `Idempotency-Key` = `mail_type/reservation_id`（24 時間有効）。`outbox.id` は使わない
- 衝突検出は `ON CONFLICT DO NOTHING RETURNING id`（UNIQUE 違反で Tx を aborted にしない）。検出時は警告ログを残し、予約操作自体は成功させる
- 順序保証は「未処理（`pending`）同士の追い越し防止」。先行が `failed` なら後続は送信される。先行がバックオフ待ち（最大 4 時間）や lease 中でも後続は待つ（**順序 > 即時性**。承認メールが受付メールを追い越さない）
- `attempt_count` は claim した回数（今回の試行を含む）。最大 6 回試行、初回失敗から最終再試行まで約 5 時間 21 分
- `failed` からの自動復帰は無い。復帰は運用手順（`docs/infrastructure.md` の Outbox 運用）による手動 SQL。Resend の Idempotency-Key は 24 時間保持され、失敗レスポンスがキャッシュされるかは公式に明記されていないため、手動再送は最終試行から 24 時間以上経ってから行う
- `reservations` 削除時は `ON DELETE CASCADE` で未送信行も消える（意図どおり。予約が無いメールは送らない）
- Domain の `MailSender` 抽象により UseCase / Outbox は Resend に依存しない

### 理由

- 送信成功直後にプロセスが落ちて `MarkSent` できないケースが典型的な二重送信源であり、論理イベントキーでの idempotency が必要
- 遷移表により各 `mail_type` は予約あたり最大 1 回なので `UNIQUE (reservation_id, mail_type)` がドメイン上も成立する

### Consequences

- (+) Resend 障害時の劣化はメール遅延に限定され、予約受付・承認は継続可能
- (+) 同一行の再送と同一論理イベントの重複 enqueue の両方を防げる
- (-) `failed` 行の滞留監視は別チャネルが必要。**監視・アラートは未決定**（当面は SQL で目視。候補は flush 内から Slack Incoming Webhook へ `failed` 行ごとに 1 回通知 + Cloud Monitoring の Scheduler ジョブ失敗アラートで「flush が動いていない」も検知する）
- (-) flush 用の private サービスと Scheduler 運用が増える
- (-) 順序保証のため、先行メールが再送待ちの間は同一予約の後続メールも遅延する

### 再検討トリガー

- Outbox `failed` が定常的に発生する場合
- メール以外の通知チャネル（ADR-016）を導入し送信経路が分岐する場合

## ADR-015: Outbox flush エンドポイントの配置

### ステータス

採用

### コンテキスト

Outbox の送信処理は HTTP の `POST /internal/outbox/flush` として公開し、**定期起動は Cloud Scheduler が行う**（間隔・再送方針は ADR-014）。問題は、この flush エンドポイントを顧客向け公開 API と同じ Cloud Run サービスに置くと、`--allow-unauthenticated`（または同等）の影響で外部から到達可能になること。

### 前提

- 公開 API は顧客ブラウザから叩くため `--allow-unauthenticated`（または同等）が必要（ADR-008）
- アプリケーションコードでの OIDC 検証は行わない方針
- 定期実行の主体は Cloud Scheduler（ADR-014）。本 ADR の対象は flush の**配置と保護**のみ

### 検討した選択肢

| 選択肢 | メリット | デメリット |
| --- | --- | --- |
| 同一サービス + アプリ内 OIDC 検証 | デプロイ 1 本 | 依存・実装が増える |
| 同一サービス + 共有シークレット | 実装が軽い | 秘密の配布・ローテーションが必要 |
| 同一イメージの private 別サービス + IAM | 認証境界が明確 | デプロイ対象が 2 つ |

### 決定

同一コンテナイメージを **公開サービス**と **private サービス**（`--no-allow-unauthenticated`）の 2 つとしてデプロイする。flush ルートは env `OUTBOX_FLUSH_ENDPOINT_ENABLED=true` のときだけ登録する（private 側のみ true）。Cloud Scheduler は private 側を OIDC で呼び、`roles/run.invoker` を付与する。

OIDC audience は Cloud Run のサービス URL（例 `https://xxx.run.app`）とし、endpoint の path / query は含めない。

### 理由

- 公開 API と内部運用エンドポイントの認証境界を分離し、設定ミスによる flush 公開の blast radius を小さくする
- Cloud Run IAM Conditions は `request.path` / `request.host` を条件にできるが、公開サービスで invoker チェックを無効化（または `allUsers`）している構成にパス条件付き IAM を重ねると壊れやすい

### Consequences

- (+) アプリ側にトークン検証コードがない
- (+) 公開サービスの設定を変えても private flush の保護は独立
- (-) CI / 運用でデプロイ手順が 1 本増える
- (-) Scheduler は稀に重複実行しうるため、handler は idempotent である必要がある（`FOR UPDATE SKIP LOCKED` + Resend Idempotency-Key で満たす）

### 再検討トリガー

- 内部エンドポイントが増え、サービス分割や Gateway が必要になった場合
- Cloud Run の認証モデル変更により単一サービスでも安全に分離できると判断した場合

## ADR-016: オーナーへの予約通知チャネル

### ステータス

一部採用（管理画面を一次手段。メール催促・LINE は未実装）

### コンテキスト

Web 予約の `pending` 滞留にオーナーが気づく手段が必要だった。かつてはメール催促や LINE Notify が候補だった。

### 前提

- 顧客向け受付・承認・拒否メールは Outbox で実装する（ADR-014）
- LINE Notify はサービス終了済み

### 決定

- オーナー向けの pending 催促メールは**実装しない**
- オーナーが新規予約に気づく一次手段は**管理画面の pending 一覧**とする（現状 UI は日付横断の pending ビューが弱く、改善は別スコープ）
- メール以外のプッシュ通知として **LINE Messaging API** を将来検討する（今回は実装しない）

### 未解決の課題

メール以外の能動通知がないため、オーナーの気づきは管理画面の能動的確認に依存する。Resend 障害時も顧客メールは遅延するが、オーナー通知チャネルは増えない。

### 再検討トリガー

- オーナーから通知の見落としが報告された場合
- pending 滞留（2 時間超）が月 1 回以上発生した場合

## ADR-017: refresh_tokens の掃除（保持ポリシー）

### ステータス

採用

### コンテキスト

`refresh_tokens` はログインと refresh ローテーションのたびに行が増えるが、期限切れ行を削除する仕組みがなく無限に成長していた。

### 前提

- 管理者は 1〜数人（ADR-000）。ログイン頻度は日〜週単位で、行数は多くても数百程度
- refresh の再利用検知（ADR-008 / `docs/table_design.md` §2.4）は revoke 済み・未期限の行に依存する

### 検討した選択肢

1. Cloud Scheduler から呼ぶ内部エンドポイント（Outbox flush と同様）
2. ログイン成功時にベストエフォートで削除
3. DB 側の定期ジョブ（pg_cron）

### 決定

**2. ログイン成功時のベストエフォート削除**を採用する。

- 削除条件は `expires_at < NOW()`（revoke 済みかどうかを問わない）。期限切れ RT は再利用検知にも使えないため安全に消せる。revoke 済み・未期限の行は残す
- `LoginUseCase` が RT 発行後、トランザクション外で `DeleteExpired` を呼ぶ。失敗はログのみで、ログインは成功させる
- `refresh_tokens.expires_at` にインデックスを追加（`000010`）

### 理由

- ADR-000 の規模では Scheduler・pg_cron などのインフラを増やす価値がない。ログイン契機で十分に行数を抑えられる
- Outbox flush エンドポイント（ADR-015）に相乗りする案は、Outbox の責務と混ざるため見送った

### Consequences

- (+) 追加インフラなし。テストはユースケースのフェイクと repository 結合テストで閉じる
- (-) 誰もログインしない期間は掃除されない（放置しても増えない限り実害なし）
- (-) ログイン成功時に DELETE が 1 回走る（インデックスありで軽微）

### 再検討トリガー

- 管理者数やログイン頻度が増え、ログイン時の DELETE が遅延として観測された場合
- Scheduler 経由の内部ジョブが他用途で増え、そこに集約した方が運用しやすくなった場合
