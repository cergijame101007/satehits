# 技術選定理由書（ADR）

## 概要

このドキュメントでは、本プロジェクトで採用した技術とその選定理由を記録する。

ADR（Architecture Decision Records）は、アーキテクチャに関する重要な決定を文書化し、将来の開発者や自分自身が「なぜこの技術を選んだのか」を理解できるようにするためのものである。

---

## ADR-001: フロントエンドフレームワーク

### ステータス

採用

### コンテキスト

予約システムのフロントエンドを構築するにあたり、フレームワークを選定する必要があった。

### 検討した選択肢

| 選択肢           | メリット                           | デメリット                             |
| ---------------- | ---------------------------------- | -------------------------------------- |
| Next.js          | 情報量多い、フルスタック           | この規模にはオーバー、Cloudflare で一部制限 |
| Astro + React    | 静的ページ高速、必要な部分だけ React | Astro の学習コスト                       |
| React + Vite (SPA) | シンプル                           | SEO 対策が手間                           |
| Nuxt 3           | Vue 好きなら最適                     | React の経験を活かせない                 |

### 決定

**Astro + React（Islands Architecture）** を採用

### 理由

1. **プロダクト特性との適合**
   - 静的コンテンツ（トップ、取引先紹介）と動的コンテンツ（予約フォーム、管理画面）が混在
   - Astro の「必要な部分だけ JS」思想が最適

2. **パフォーマンス**
   - 静的ページは JS 0KB で配信可能
   - Core Web Vitals で有利

3. **開発体験**
   - React の知識をそのまま活用可能
   - Vite 内蔵で高速な HMR

4. **Cloudflare Pages との相性**
   - 静的出力がデフォルト
   - エッジでの配信に最適化

### 結果

- トップページ等は `.astro` で高速に配信
- 予約フォーム等は React Islands で実装

## ADR-002: ホスティング（フロントエンド）

### ステータス

採用

### コンテキスト

フロントエンドのホスティング先を選定する必要があった。

### 検討した選択肢

| 選択肢           | メリット                 | デメリット             |
| ---------------- | ------------------------ | ---------------------- |
| Vercel           | Next.js 最適化、情報多い   | 帯域課金、この規模には過剰 |
| Cloudflare Pages | 帯域無制限、CDN 強力       | Next.js より情報少ない   |
| Netlify          | 使いやすい               | 帯域制限あり           |

### 決定

**Cloudflare Pages** を採用

### 理由

1. **コスト**
   - 帯域無制限（無料枠）
   - 小規模プロジェクトに最適

2. **Cloudflare 統一**
   - ドメイン（Cloudflare Registrar）と一元管理
   - DNS 設定が簡単

3. **Astro との相性**
   - 静的サイトのホスティングに最適
   - ビルド・デプロイが高速

## ADR-003: スタイリング

### ステータス

採用

### コンテキスト

UI のスタイリング手法を選定する必要があった。

### 検討した選択肢

| 選択肢       | メリット                 | デメリット           |
| ------------ | ------------------------ | -------------------- |
| Tailwind CSS | 開発速度、一貫性         | クラス名が長くなる   |
| CSS Modules  | スコープ明確             | 開発速度がやや遅い   |
| 素の CSS       | 学習コスト 0               | 大規模で管理困難     |
| CSS-in-JS    | コンポーネント完結       | Astro との相性△       |

### 決定

**Tailwind CSS v4 + カスタムアニメーション** を採用

### 理由

1. **開発速度**
   - ユーティリティクラスで素早くスタイリング
   - デザインシステムの一貫性を保ちやすい

2. **Astro との相性**
   - 公式インテグレーション（`@astrojs/tailwind`）
   - ビルド時に未使用クラスを除去

3. **アニメーション**
   - 基本は Tailwind のユーティリティ
   - 複雑なものは `<style>` タグでカスタム CSS

## ADR-004: メール送信サービス

### ステータス

採用

### コンテキスト

予約確認メールや通知メールを送信するサービスを選定する必要があった。

### 検討した選択肢

| 選択肢   | 無料枠       | メリット             | デメリット       |
| -------- | ------------ | -------------------- | ---------------- |
| SendGrid | 100 通/日     | 実績豊富、安定       | API がやや複雑     |
| Resend   | 3,000 通/月   | API シンプル、モダン   | 新しいサービス   |
| AWS SES  | 62,000 通/月  | 最安                 | 設定が複雑       |

### 決定

**Resend** を採用

### 理由

1. **開発体験**
   - API がシンプル
   - Go SDK あり
   - デバッグ用ログあり

2. **無料枠**
   - 3,000 通/月は予約通知に十分

3. **この規模に適切**
   - SendGrid はエンタープライズ向け機能が多すぎる
   - Resend は必要十分

## ADR-005: バックエンドアーキテクチャ

### ステータス

採用

### コンテキスト

バックエンドのアーキテクチャパターンを選定する必要があった。

### 検討した選択肢

| 選択肢                       | メリット                   | デメリット             |
| ---------------------------- | -------------------------- | ---------------------- |
| レイヤード + Repository + DI | バランス良い、テスト容易   | 多少のボイラープレート |
| クリーンアーキテクチャ       | 疎結合                     | この規模には過剰       |
| フル DDD                       | ドメイン表現力             | 明らかに過剰           |
| シンプル MVC                   | 学習コスト低               | テスト困難、肥大化     |

### 決定

**レイヤードアーキテクチャ + Repository + DI** を採用

### 理由

1. **プロダクト規模に適切**
   - ドメインの複雑さ: 低〜中
   - チーム: 1 人開発

2. **テスト容易性**
   - Repository インターフェースでモック可能
   - DI で依存を注入

3. **将来の拡張**
   - 必要に応じて Domain Service を追加可能
   - クリーンアーキテクチャへの移行も可能

## ADR-006: ランタイム・パッケージマネージャ

### ステータス

採用

### コンテキスト

フロントエンドの JavaScript ランタイムとパッケージマネージャを選定する必要があった。

### 検討した選択肢

| 選択肢         | メリット               | デメリット       |
| -------------- | ---------------------- | ---------------- |
| bun            | 高速、オールインワン   | 一部互換性問題   |
| Node.js + pnpm | 安定、互換性高い       | bun より遅い       |
| Node.js + npm  | 最も安定               | 遅い             |

### 決定

**bun** を採用

### 理由

1. **速度**
   - インストール、実行が高速
   - 開発体験向上

2. **オールインワン**
   - ランタイム + パッケージマネージャ + バンドラ
   - ツールチェーンがシンプル

3. **Astro との相性**
   - 公式で bun サポート
