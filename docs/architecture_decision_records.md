# 技術選定理由書（ADR）

## 概要

このドキュメントでは、本プロジェクトで採用した技術とその選定理由を記録する。

ADR（Architecture Decision Records）は、アーキテクチャに関する重要な決定を文書化し、将来の開発者や自分自身が「なぜこの技術を選んだのか」を理解できるようにするためのものである。

**ADR-000** は他のすべての ADR が参照する「想定規模」の共通前提である。ADR-001 以降の「この規模には過剰」という判断の妥当性は、ここに定義した数値に対して検証する。

---

## ADR-000: 想定規模の前提

### ステータス

暫定（推定値・**リリース後の実測による更新必須**）

### コンテキスト

ADR-001 以降の技術選定では「この規模には過剰」という判断を複数回行っている。しかしその「規模」が定義されていなければ、判断の妥当性を後から検証できず、いつ判断が無効になるのかも分からない。

本 ADR は、他のすべての ADR が参照する共通の前提数値を定義する。
リリース前のため実測値は存在せず、以下はすべて店舗の営業条件から導出した推定値である。

事業上の物理制約（営業日・提供数など）の確定値は [`domain_knowledge.md`](./domain_knowledge.md) を正とする。本 ADR はそれらから導出した負荷・集客の推定と、技術選定への影響範囲を扱う。

---

### 1. 事業上の物理制約（確定値）

店舗営業条件の正は [`domain_knowledge.md`](./domain_knowledge.md) である。本節はその要約と、規模推定用の計算である。

| 項目 | 値 | 出典・注記 |
|---|---|---|
| 定例の営業曜日 | 月・火・水・土・日（木・金は定休日） | `domain_knowledge` |
| 祝日 | 通常営業（11:30–15:00）。祝が日曜に重なる場合は `daily_schedules` で設定 | 同上。定例合成は曜日ベースのため、祝の開閉はオーナー設定が正 |
| 営業時間 | 月火水土祝: 11:30–15:00（ランチ）。**日曜は 8:30–15:00（朝営業あり）** | 同上。日曜の朝帯は予約不可・来店順 |
| 提供数（定例デフォルト） | **1日最大10食**（オーナーが日ごとに変更可能） | 同上。システム上の絶対上限ではない |
| 月間営業日数（定例ベース） | 約21.5日（週5日 × 4.3週） | 計算。祝が木・金に重なると営業日が増えうる |
| **月間提供数の定例理論上限** | **約215食** | 10食 × 21.5日。下記の「天井」の意味を参照 |

**「約215食」の位置づけ**

- 定例デフォルト（週5・1日10食）から導く**規模感の目安**であり、ハードキャップではない。
- 日別の提供数変更、店内イベント、祝日による営業日増、臨時休業・外部イベントによる減により、実月の提供数はこの前後に振れる（イベント等で月+20〜40食程度を見込みうる）。
- 以下の負荷推定は、この定例目安の内側〜その近傍に収まる想定である。

### 2. 集客チャネルと流入推定

現時点の主要な集客手段は Instagram（フォロワー1,581名 / 111投稿 / 週次でメニュー更新）であり、広告出稿は行っていない。

| 経路 | 月間セッション | 根拠 |
|---|---|---|
| Instagram | 150〜400 | フォロワー1,581名。週次投稿+ストーリーからのプロフィール／リンク遷移を投稿あたり5〜20と想定 |
| Google 指名検索・マップ | 100〜250 | 店名で検索する層。個人飲食店では最大の流入源となることが多い |
| 非指名検索 | 30〜120 | 「富山 ヴィーガン ランチ」「砂糖不使用 御膳」等。コンセプトが明確で競合は少ないが、検索母数自体が小さい |
| 直接・その他 | 30〜80 | 再訪、口コミ、ショップカード等 |
| **合計** | **300〜800（中央値 500）** | |

### 3. 導出した前提値

| 項目 | 推定値 | 導出過程 | 確度 |
|---|---|---|---|
| 月間セッション | 300〜800（中央値500） | 上記チャネル別推定の合計 | 低 |
| 月間予約件数 | 60〜120 | 定例上限215食 ÷ 平均1.8名/組 ≒ 119組。稼働率50〜100%を想定（Web・Instagram・電話等の経路合算） | 中 |
| 月間メール送信数 | 120〜300通 | Web予約は顧客向け最大2通（受付確認＋承認。拒否時は受付＋拒否で同様に2通）。オーナー手動登録はメールなし。システム上のキャンセル・変更メールは無し（連絡は Instagram DM） | 中 |
| バックエンドリクエスト | 月1,000〜3,000 | 静的アセットはCloudflareのエッジで完結するため、オリジンに到達するのは空き枠取得APIと予約POST、および管理画面操作のみ | 中 |
| ピーク同時アクセス | 10未満 | Instagram投稿直後・イベント告知直後の1〜2時間に50〜100セッションが集中しても、秒間1リクエストに満たない | 中 |
| DBレコード増加量 | 予約 年間1,000〜1,400件 | 月60〜120件 × 12ヶ月。数年運用してもデータ量は数MB規模 | 中 |

**確度の定義**

- 高: 業務フローから直接算出でき、集客状況に依存しない
- 中: 定例の物理上限が効くため、外しても桁は変わりにくい（または経路・承認結果で通数が振れる）
- 低: 外部要因に依存し、実測との乖離が大きくなりうる

**メール通数の補足**

- 現行の送信種別は顧客向けの受付・承認・拒否のみ（オーナー宛の予約ごと通知は未実装。UC-S04 リマインドは別途）。
- 月間予約の一部は Instagram / 電話等の手動登録のため、メール対象は Web 経路に偏る。上記 120〜300 はその前提の概算である。

---

### 4. この前提に依存している決定

数値が変わった場合に再検討が必要になる ADR を明示する。

| 前提 | 依存するADR | 前提が崩れた場合の影響 |
|---|---|---|
| 月間メール 120〜300通 | ADR-004（Resend） | 無料枠3,000通/月を超えるとコストが発生。AWS SESへの移行検討が必要 |
| ピーク同時 10未満 | ADR-002（Cloudflare Pages）<br>ADR-005（バックエンド構成） | 大幅に超える場合、キャッシュ戦略とスケーリングの検討が必要 |
| 月間セッション 300〜800 | ADR-001（Astro）<br>ADR-002（Cloudflare Pages） | 帯域・ビルド回数ともに無料枠内。桁が変わらない限り再検討不要 |
| 予約 年間1,000件強 | ADR-005（DB構成） | データ量・インデックス設計に影響。桁が2つ変わるまで現行構成で十分 |

**補足: 負荷はボトルネックではない**

上記の通り、トラフィック起因の技術的リスクは実質的に存在しない。
一方、定例でも1日あたり最大10食程度という供給の少なさにより、**イベント告知直後に残り僅少の枠へ複数の予約が同時に到達する**状況は現実的に発生しうる。

したがって本プロダクトにおける主要な技術的関心はスケーラビリティではなく**同時予約時の整合性（ダブルブッキングの防止）**であり、限られた実装工数はそちらに優先的に配分する。

| 指標 | 測定手段 |
|---|---|

### 6. 更新ルール

> **本ADRの数値はすべてリリース前の推定であり、実測値による更新を必須とする。**

| タイミング | 対応 |
|---|---|
| リリース後1ヶ月 | 初回の実測値を記録し、推定との乖離を確認する |
| **リリース後3ヶ月** | **全項目を実測値に置き換え、確度を「高」に更新する（必須）** |
| 以後 | 年1回、または下記トリガー該当時に見直す |

**即時見直しトリガー**

- 月間メール送信数が 1,500通 を超えた場合 → ADR-004 を再評価
- 月間セッションが 2,000 を超えた場合 → ADR-001 / ADR-002 を再評価
- ピーク時にレスポンス遅延・エラーが観測された場合 → ADR-005 を再評価
- 営業日数・提供食数・営業形態が変更された場合 → 本ADRを即時改訂（`domain_knowledge` と同時に）

推定値のまま放置された前提は、根拠のない数値として後続のすべての判断の信頼性を損なう。実測値への置き換えは本ADRの完了条件である。

## ADR-001: フロントエンドフレームワーク

### ステータス

採用

### コンテキスト

予約システムのフロントエンドを構築するにあたり、フレームワークを選定する必要があった。

### 検討した選択肢

| 選択肢           | メリット                           | デメリット                             |
| ---------------- | ---------------------------------- | -------------------------------------- |
| Next.js          | 情報量多い、フルスタック           | この規模にはオーバー、Cloudflare で一部制限 |
| Astro + React    | 静的ページ高速、必要な部分だけ React | Astro の学習コスト                       |
| React + Vite (SPA) | シンプル                           | SEO 対策が手間                           |
| Nuxt 3           | Vue 好きなら最適                     | React の経験を活かせない                 |

### 決定

**Astro + React（Islands Architecture）** を採用

### 理由

1. **プロダクト特性との適合**
   - 静的コンテンツ（トップ、取引先紹介）と動的コンテンツ（予約フォーム、管理画面）が混在
   - Astro の「必要な部分だけ JS」思想が最適

2. **パフォーマンス**
   - 静的ページは JS 0KB で配信可能
   - Core Web Vitals で有利

3. **開発体験**
   - React の知識をそのまま活用可能
   - Vite 内蔵で高速な HMR

4. **Cloudflare Pages との相性**
   - 静的出力がデフォルト
   - エッジでの配信に最適化

### 結果

- トップページ等は `.astro` で高速に配信
- 予約フォーム等は React Islands で実装

## ADR-002: ホスティング（フロントエンド）

### ステータス

採用

### コンテキスト

フロントエンドのホスティング先を選定する必要があった。

### 検討した選択肢

| 選択肢           | メリット                 | デメリット             |
| ---------------- | ------------------------ | ---------------------- |
| Vercel           | Next.js 最適化、情報多い   | 帯域課金、この規模には過剰 |
| Cloudflare Pages | 帯域無制限、CDN 強力       | Next.js より情報少ない   |
| Netlify          | 使いやすい               | 帯域制限あり           |

### 決定

**Cloudflare Pages** を採用

### 理由

1. **コスト**
   - 帯域無制限（無料枠）
   - 小規模プロジェクトに最適

2. **Cloudflare 統一**
   - ドメイン（Cloudflare Registrar）と一元管理
   - DNS 設定が簡単

3. **Astro との相性**
   - 静的サイトのホスティングに最適
   - ビルド・デプロイが高速

## ADR-003: スタイリング

### ステータス

採用

### コンテキスト

UI のスタイリング手法を選定する必要があった。

### 検討した選択肢

| 選択肢       | メリット                 | デメリット           |
| ------------ | ------------------------ | -------------------- |
| Tailwind CSS | 開発速度、一貫性         | クラス名が長くなる   |
| CSS Modules  | スコープ明確             | 開発速度がやや遅い   |
| 素の CSS       | 学習コスト 0               | 大規模で管理困難     |
| CSS-in-JS    | コンポーネント完結       | Astro との相性△       |

### 決定

**Tailwind CSS v4 + カスタムアニメーション** を採用

### 理由

1. **開発速度**
   - ユーティリティクラスで素早くスタイリング
   - デザインシステムの一貫性を保ちやすい

2. **Astro との相性**
   - 公式インテグレーション（`@astrojs/tailwind`）
   - ビルド時に未使用クラスを除去

3. **アニメーション**
   - 基本は Tailwind のユーティリティ
   - 複雑なものは `<style>` タグでカスタム CSS

## ADR-004: メール送信サービス

### ステータス

採用

### コンテキスト

予約確認メールや通知メールを送信するサービスを選定する必要があった。

### 検討した選択肢

| 選択肢   | 無料枠       | メリット             | デメリット       |
| -------- | ------------ | -------------------- | ---------------- |
| SendGrid | 100 通/日     | 実績豊富、安定       | API がやや複雑     |
| Resend   | 3,000 通/月   | API シンプル、モダン   | 新しいサービス   |
| AWS SES  | 62,000 通/月  | 最安                 | 設定が複雑       |

### 決定

**Resend** を採用

### 理由

1. **開発体験**
   - API がシンプル
   - Go SDK あり
   - デバッグ用ログあり

2. **無料枠**
   - 3,000 通/月は予約通知に十分

3. **この規模に適切**
   - SendGrid はエンタープライズ向け機能が多すぎる
   - Resend は必要十分

## ADR-005: バックエンドアーキテクチャ

### ステータス

採用

### コンテキスト

バックエンドのアーキテクチャパターンを選定する必要があった。

### 検討した選択肢

| 選択肢                       | メリット                   | デメリット             |
| ---------------------------- | -------------------------- | ---------------------- |
| レイヤード + Repository + DI | バランス良い、テスト容易   | 多少のボイラープレート |
| クリーンアーキテクチャ       | 疎結合                     | この規模には過剰       |
| フル DDD                       | ドメイン表現力             | 明らかに過剰           |
| シンプル MVC                   | 学習コスト低               | テスト困難、肥大化     |

### 決定

**レイヤードアーキテクチャ + Repository + DI** を採用

### 理由

1. **プロダクト規模に適切**
   - ドメインの複雑さ: 低〜中
   - チーム: 1 人開発

2. **テスト容易性**
   - Repository インターフェースでモック可能
   - DI で依存を注入

3. **将来の拡張**
   - 必要に応じて Domain Service を追加可能
   - クリーンアーキテクチャへの移行も可能

## ADR-006: ランタイム・パッケージマネージャ

### ステータス

採用

### コンテキスト

フロントエンドの JavaScript ランタイムとパッケージマネージャを選定する必要があった。

### 検討した選択肢

| 選択肢         | メリット               | デメリット       |
| -------------- | ---------------------- | ---------------- |
| bun            | 高速、オールインワン   | 一部互換性問題   |
| Node.js + pnpm | 安定、互換性高い       | bun より遅い       |
| Node.js + npm  | 最も安定               | 遅い             |

### 決定

**bun** を採用

### 理由

1. **速度**
   - インストール、実行が高速
   - 開発体験向上

2. **オールインワン**
   - ランタイム + パッケージマネージャ + バンドラ
   - ツールチェーンがシンプル

3. **Astro との相性**
   - 公式で bun サポート
